# ESPnet

ESPnet is an end-to-end speech processing toolkit built on PyTorch: speech
recognition, text-to-speech, speech translation, enhancement, speaker tasks,
diarization, spoken language understanding, singing voice synthesis, speech
language models, and more, with Kaldi-style reproducible recipes and pretrained
models on Hugging Face. Apache 2.0 licensed.

Supported versions are declared in `pyproject.toml`: Python 3.12 to 3.13 and
PyTorch/torchaudio 2.9.1 to 2.11.0. Code must work across that whole range.

This file gives Claude Code the project conventions. The automatic PR review
(`.github/workflows/claude-code-review.yml`) reports newly introduced
violations of the rules below, so keep them specific and keep them true.

## Repository layout

| Path | What it is |
|---|---|
| `espnet2/` | The main toolkit. One package per task (`asr`, `tts`, `enh`, `st`, `spk`, `speechlm`, ...), shared code in `layers/`, `train/`, `torch_utils/`, `fileio/`, `text/`, and command-line entry points in `bin/`. |
| `espnet2/tasks/` | `AbsTask` subclasses that wire model, data pipeline and trainer together for each task. |
| `espnet2/legacy/` | Code inherited from ESPnet1. Bug fixes only; no new features. |
| `espnet3/` | The next-generation toolkit: Hydra/OmegaConf configs, Lightning-based training, Dask parallelism, Hugging Face `datasets`. `systems/` holds task systems (asr, tts), `components/` the building blocks. |
| `egs2/` | ESPnet2 recipes, one directory per corpus and task, e.g. `egs2/librispeech/asr1/`. `egs2/TEMPLATE/<task>1/` holds the shared pipelines (`asr.sh`, `tts.sh`, `enh.sh`, ...) that recipes symlink to. |
| `egs3/` | ESPnet3 recipes (`egs3/librispeech_100/asr/`, `egs3/mini_an4/`), each a `run.py` with stages `create_dataset`, `train`, `infer`, `measure` and configs in `conf/`. Templates in `egs3/TEMPLATE/`. |
| `test/espnet2/`, `test/espnet3/` | pytest suites mirroring the package layout. |
| `test_utils/` | bats tests for shell scripts and `utils/` tools. |
| `utils/` | Lightweight, self-contained Python and bash tools. |
| `tools/` | Environment setup and optional installers (`tools/installers/`). |
| `ci/` | Scripts run by GitHub Actions (`test_python_espnet2.sh`, `test_shell_espnet2.sh`, `test_integration_espnet2.sh`, ...). |
| `doc/` | Sphinx documentation sources. |

ESPnet1 (`espnet/`, `egs/`) has been removed and is no longer supported.
`egs2/TEMPLATE/asr1/utils`, `egs2/TEMPLATE/asr1/steps` and
`egs2/TEMPLATE/tts1/sid` are vendored Kaldi scripts and are excluded from
formatting and linting; changes there need a strong reason.

## Setup and everyday commands

```bash
pip install -e ".[test]"        # ".[all]" adds the optional task dependencies
. tools/activate_python.sh      # generated by tools/setup_venv.sh (or another
                                # tools/setup_*.sh); CI and recipes source it

# Unit tests (CI runs each test with a 10 s timeout)
pytest -q test/espnet2/asr/test_ctc.py
./ci/test_python_espnet2.sh     # full espnet2 suite with coverage
./ci/test_python_espnet3.sh     # espnet3 suite, includes flake8-docstrings

# Style. pre-commit.ci also runs black and isort on every PR.
black <paths> && isort <paths>
pycodestyle --show-source <paths>
python utils/apply_code_fixes.py <folder>   # fixes most style findings

# Shell scripts: shellcheck + bats
./ci/test_shell_espnet2.sh
```

Tool configuration lives in `setup.cfg` (flake8/pycodestyle with
`max-line-length = 88` and the shared ignore list, `isort` profile black,
pytest options) and `.pre-commit-config.yaml` (black, isort, trailing
whitespace, end-of-file newline, YAML syntax, large-file check).

## Coding conventions

### Python

- Format with `black` and `isort` (profile black), 88-column lines, PEP 8, and
  Google-style docstrings. Public functions and classes get a docstring; code
  under `espnet3/` must pass `flake8-docstrings`.
- Stay within the supported Python and PyTorch ranges. An API that exists only
  in newer versions needs a version guard, as done with `is_torch_2_6_plus`
  in `espnet2/torch_utils/safe_torch_load.py`.
- Load checkpoints and other pickled tensors with
  `espnet2.torch_utils.safe_torch_load.safe_torch_load`, not bare
  `torch.load`. Never pass `weights_only=False` and never set
  `ESPNET_ALLOW_UNSAFE_TORCH_LOAD` from library code; the unsafe fallback is
  an explicit user decision made at run time.
- Keep task-agnostic code in `espnet2/layers/`, `espnet2/torch_utils/`,
  `espnet2/train/`; task-specific code belongs to its task package. Do not
  add features under `espnet2/legacy/`.
- Do not add packages to the base `dependencies` list in `pyproject.toml`.
  Optional or task-specific packages go into the matching extra (`asr`,
  `tts`, `enh`, `speechlm`, ...) or into `tools/installers/`, and their
  imports must be guarded so the base install keeps working. `kaldiio` stays
  out of the base dependencies because of its license (issue #6529).
- Command-line tools in `espnet2/bin/` and `utils/` define
  `get_parser() -> argparse.ArgumentParser` with a `description`, so the
  documentation can be generated. A new `utils/` tool needs a bats test in
  `test_utils/`.
- Changes to model or config schemas must keep loading the released models on
  Hugging Face and their `config.yaml`. When a key is renamed, keep accepting
  the old one with a deprecation warning.

### Bash and recipes

- Scripts use `set -e`, `set -u`, `set -o pipefail`, the `log()` helper, and
  `utils/parse_options.sh` for arguments, and pass shellcheck with the flags
  used in `ci/test_shell_espnet2.sh` (`-e SC2001 -e SC1091 -e SC2086`).
- Create a new ESPnet2 recipe with
  `egs2/TEMPLATE/<task>1/setup.sh egs2/<corpus>/<task>1`. Shared files
  (`asr.sh`, `path.sh`, `db.sh`, `scripts`, `pyscripts`, `steps`, `utils`)
  must stay symlinks into `egs2/TEMPLATE/<task>1/`, never copies.
  Corpus-specific code goes in `local/`, with `local/data.sh` preparing the
  Kaldi-style `data/` directories (`wav.scp`, `text`, `utt2spk`, `spk2utt`).
- Default configurations are `conf/train.yaml` and `conf/decode.yaml`;
  variants go in `conf/tuning/` and are named after what differs. Cluster
  settings (`cmd.sh`, `conf/slurm.conf`, `conf/queue.conf`, `conf/pbs.conf`)
  stay at the template defaults.
- A new corpus gets an entry in `egs2/TEMPLATE/asr1/db.sh` (most task
  templates symlink to it) and a row in `egs2/README.md`. Do not commit data,
  or large metadata such as lexicons or keyword lists, into the recipe.
- Report results in the recipe's `README.md`, ideally with a link to the
  trained model on Hugging Face.

## Tests

- Every new module or bug fix in `espnet2/` or `espnet3/` comes with a test
  under the mirrored path in `test/espnet2/` or `test/espnet3/`, in a file
  named `test_<module>.py` with `test_*` functions. One test file per source
  file; prefer several small files over one large one.
- Tests run on CPU with tiny models and must finish within the 10 s CI
  timeout; use `@pytest.mark.execution_timeout(sec)` for justified
  exceptions. No network downloads, no large files, no GPU requirement.
- New command-line features in `espnet2/bin/` need a case in
  `ci/test_integration_espnet2.sh` on `egs2/mini_an4`, calling scripts with
  `--python "${python}"` so coverage is recorded, never plain `python`.

## Pull requests

- Keep PRs small: at most 20 changed files and fewer than 1000 changed lines,
  unless the change is a refactor or reformatting agreed with maintainers.
  Split larger work.
- One concern per PR. Do not mix reformatting or renames with behaviour
  changes.
- Fill in the PR template: what changed, why, and confirm the size limit.
- Pin GitHub Actions to a full commit SHA with a `# vN` comment, as the
  existing workflows do.
- Required checks are `ci_gate_ubuntu`, `ci_gate_macos`, `ci_gate_windows`
  and `ci_gate_debian12`; pre-commit.ci and Codecov also run on every PR.

## Claude Code in this repository

- `@claude <request>` in a PR or issue comment runs the interactive workflow
  in `.github/workflows/claude.yml`. The commenter needs write access to the
  repository.
- Automatic review (`.github/workflows/claude-code-review.yml`) runs on PRs
  from owners, members and collaborators. For other contributors a maintainer
  adds the `claude-review` label. A review can also be started from the
  Actions tab with the PR number.
